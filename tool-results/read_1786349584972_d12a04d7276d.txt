   141→ 1. Executive Summary
   142→ This report presents the findings of a comprehensive white-box security audit conducted on the Superboard
   143→ platform, a real-time collaborative whiteboard and virtual classroom application built with Next.js 16,
   144→ Hocuspocus (Yjs/CRDT), LiveKit (WebRTC), Tldraw (vector canvas), Supabase (authentication and
   145→ database), and Stripe (payment processing). The audit examined all source code repositories, API routes,
   146→ WebSocket servers, infrastructure configurations, and frontend components across five distinct audit phases as
   147→ defined in the White-Box Audit Master Plan.
   148→
   149→ The assessment identified a total of 52 security findings across all system layers: 10 Critical, 14 High, 18
   150→ Medium, and 10 Low severity. The most severe vulnerabilities center on three primary attack surfaces: (1)
   151→ missing or bypassable authentication on critical endpoints including WebSocket connections, room join
   152→ operations, and parent portal access; (2) insufficient authorization enforcement allowing privilege escalation
   153→ from student to tutor roles in both the real-time collaboration layer and the WebRTC media pipeline; and (3)
   154→ weakened Content Security Policy that generates cryptographic nonces but fails to use them, leaving all inline
   155→ script execution unrestricted.
   156→
   157→ The platform demonstrates evidence of prior security remediation efforts, with multiple SECURITY FIX
   158→ annotations referencing specific vulnerability identifiers (V-06 through V-34, I-02 through I-05).
   159→ Authentication enforcement on API routes is generally strong, with most endpoints correctly invoking
   160→ requireAuth() or requireAdmin() helpers. The Prisma ORM provides strong SQL injection protection, Zod
   161→ schemas validate most user inputs, and security headers including HSTS, X-Frame-Options, and
   162→ X-Content-Type-Options            are   properly   configured.     However,      the     real-time   collaboration   layer
   163→ (Hocuspocus/Yjs) and the WebRTC signaling pipeline contain fundamental authentication gaps that
   164→ undermine the otherwise solid application-level security.
   165→
   166→ Immediate remediation of all 10 Critical findings is strongly recommended before any further production
   167→ deployment. These vulnerabilities, if exploited, could allow unauthorized access to live tutoring sessions,
   168→ exposure of student personally identifiable information (PII), forgery of video conferencing tokens, and
   169→ server-side request forgery attacks against internal infrastructure. The estimated total remediation effort is
   170→ approximately 3-4 developer-sprints, with Critical items addressable within the first sprint.

   414→ 3. Architecture and State Bottleneck Analysis
   415→ 3.1 Real-Time Engine Architecture
   416→ The Superboard real-time collaboration engine is built on a three-layer architecture: Tldraw provides the
   417→ vector canvas rendering on the frontend, Hocuspocus serves as the WebSocket server managing Yjs document
   418→ synchronization, and PostgreSQL (via Prisma) persists document snapshots. The system uses a snapshot-based
   419→ synchronization approach rather than fine-grained operational transformation, which introduces specific
   420→ latency and consistency characteristics that were analyzed during this audit.
   421→
   422→ The most significant architectural bottleneck identified is the snapshot-based sync mechanism in
   423→ TldrawCanvas.tsx. Rather than using the official @tldraw/yjs binding that integrates Tldraw's store directly
   424→ with Yjs shared types at the individual operation level, the current implementation serializes the entire editor
   425→ state to JSON on each change with a 500ms debounce interval. This creates a last-writer-wins race condition
   426→
   427→
   428→
   429→
   430→                                                                                                                                Page 8
   431→Superboard Security Audit Report                                                                   CONFIDENTIAL
   432→
   433→
   434→
   435→
   436→ where concurrent edits from multiple users result in data loss. When two users draw simultaneously, the last
   437→ snapshot to arrive overwrites the other user's changes within the debounce window. This fundamentally
   438→ undermines the collaborative editing experience and represents a data integrity risk in production tutoring
   439→ sessions.
   440→
   441→ The Hocuspocus server is configured with IP-based connection rate limiting (30 connections per minute) but
   442→ lacks per-connection message rate limiting, payload size limits (maxDocumentSize is not set), and the room
   443→ membership verification is entirely commented out. The persistence layer implements a 5MB size check on
   444→ document snapshots but this only triggers during store operations, not on inbound WebSocket messages,
   445→ meaning oversized payloads can accumulate in server memory before being rejected.
   446→
   447→
   448→ 3.2 WebSocket Authentication Gap
   449→ The Hocuspocus server defines an onAuthenticate hook that validates Supabase JWT tokens and extracts the
   450→ userId from the connection context. However, the client-side useYjsProvider hook creates the
   451→ HocuspocusProvider with zero authentication parameters - no token, no parameters, and no WebSocket
   452→ subprotocol authentication headers are passed. This means the WebSocket connection either fails silently (if
   453→ onAuthenticate is strictly enforced by Hocuspocus v4) or, more critically, proceeds without any authentication
   454→ if the hook is lenient. The room membership check within onAuthenticate is entirely commented out with a
   455→ TODO note, meaning even if authentication were properly wired, any authenticated user could connect to any
   456→ room's CRDT document.
   457→
   458→ This represents a fundamental security gap in the real-time collaboration layer. An unauthenticated or
   459→ cross-tenant attacker connecting to the WebSocket can read the full whiteboard state (all drawings, text
   460→ annotations, page content) and inject arbitrary data into the document. For a tutoring platform handling student
   461→ work and lesson content, this is a severe confidentiality and integrity violation. The remediation requires
   462→ wiring the Supabase session token from the client to the Hocuspocus connection parameters and
   463→ uncommenting and implementing the room membership verification logic.
   464→
   465→
   466→ 3.3 WebRTC Media Pipeline
   467→ The LiveKit integration for video conferencing has two critical security weaknesses. First, the token
   468→ generation endpoint trusts the client-supplied isTutor field without server-side verification against the
   469→ database. When isTutor is undefined (the default when a student omits it), the expression canPublish: isTutor
   470→ !== false evaluates to true, granting the student full media publishing permissions including camera,
   471→ microphone, and screen sharing. Second, when the LiveKit SDK throws an error or the API key is not
   472→ configured, the endpoint falls back to generating mock tokens with a trivially forgeable .mock_signature suffix
   473→ or a mock_token_{roomId}_{userId} string pattern.
   474→
   475→ The LiveKit webhook endpoint, which receives recording status updates, uses a static Bearer token comparison
   476→ that is vulnerable to timing side-channel attacks. More critically, the authentication check is completely
   477→ skipped when the LIVEKIT_WEBHOOK_SECRET environment variable starts with "TODO_" or is empty.
   478→ In a production environment, this would allow any attacker to send fake recording events to manipulate
   479→ recording statuses or trigger unauthorized recording state changes.

   490→ 3.4 Frontend Canvas Performance Concerns
   491→ The TldrawCanvas component implements canvas rendering using the Tldraw library which handles vector
   492→ path rendering, object management, and viewport transformations. The snapshot-based sync approach means
   493→ every 500ms, the entire canvas state is serialized and transmitted as a single JSON payload. For a 90-minute
   494→ tutoring session generating tens of thousands of vector paths, this creates substantial memory pressure on both
   495→ the client and server. The persistence layer stores these snapshots as Text fields in PostgreSQL with a 5MB
   496→ constraint, but there is no client-side mechanism to prune deleted objects from memory or to implement
   497→ incremental state compression.
   498→
   499→ Input event throttling analysis shows that pointermove and touchmove events are processed at browser native
   500→ frequency (typically 60-120Hz) before being debounced by the 500ms sync interval. While Tldraw handles its
   501→ own rendering pipeline efficiently, the lack of intermediate point simplification (e.g., Douglas-Peucker
   502→ algorithm) before JSON serialization means raw coordinate data is transmitted in full, increasing WebSocket
   503→ bandwidth consumption. The combination of no client-side path simplification, snapshot-based sync, and lack
   504→ of memory management creates a performance degradation risk for long-duration sessions on lower-end
   505→ devices.

   510→ 4. Code Remediation Patches
   511→ This chapter provides exact code-level remediation recommendations for all Critical and High severity
   512→ findings. Each patch includes the specific file path, line numbers, current vulnerable code, and the
   513→ recommended replacement code. Patches are designed to be minimal and surgical to reduce regression risk
   514→ during implementation.

   669→ 5. Compliance, Recording and Data Privacy
   670→ 5.1 COPPA and FERPA Considerations
   671→ The Superboard platform processes educational data from K-12 students, placing it squarely within the scope
   672→ of the Children's Online Privacy Protection Act (COPPA) and the Family Educational Rights and Privacy Act
   673→ (FERPA). Several identified vulnerabilities directly impact compliance with these regulations. The
   674→ unauthenticated room join endpoint (API-C01) can expose student names, emails, and enrollment status to
   675→ unauthorized parties. The parent portal (API-C02), while designed for legitimate parental access, lacks
   676→ brute-force protection on its URL-path tokens, potentially allowing unauthorized access to student homework,
   677→ lesson notes, schedule information, and tutor contact details.
   678→
   679→ Recording URLs (RT-M03) are served without signed access controls, meaning anyone with the URL can
   680→ download video recordings of tutoring sessions. These recordings contain video and voice data of minor
   681→ students, which constitutes protected educational records under FERPA. The calendar ICS endpoint
   682→ (API-C03) exposes student and tutor email addresses to anyone with a lesson UUID, constituting a personally
   683→ identifiable information disclosure. Under COPPA, the platform must obtain verifiable parental consent
   684→ before collecting personal information from children under 13, and the current authentication gaps could allow
   685→ data collection without proper consent verification.
   686→
   687→
   688→ 5.2 Data Retention and Encryption
   689→ The platform stores board page snapshots as Text fields in PostgreSQL with a 5MB constraint. Recordings are
   690→ stored via LiveKit Egress, with URLs persisted in the Recording model. There is no evidence of
   691→ encryption-at-rest configuration for PostgreSQL data, and recording storage encryption depends on the
   692→ underlying LiveKit Egress configuration. The database schema does not include automatic data retention
   693→ policies or TTL mechanisms for usage logs, recordings, or session data. For COPPA/FERPA compliance, the
   694→ platform should implement automatic data retention limits with configurable expiry periods for student-related
   695→ data, ensure all recordings are encrypted at rest using AES-256, and serve recording URLs via signed, expiring
   696→ URLs rather than direct storage links.
   697→
   698→
   699→ 5.3 Service Worker Privacy Concerns
   700→ The service worker (sw.js) implements a stale-while-revalidate caching strategy for all non-API GET requests.
   701→ This means authenticated pages including the dashboard, room views, and admin panel are cached in the
   702→ browser and can be served to subsequent users of the same device. On shared devices (common in school
   703→ computer labs and library settings), this creates a user-to-user information leak where Student B may see
   704→ Student A's dashboard content including name, email, tier, room list, and usage data before the revalidation
   705→ request completes. The service worker should skip caching for authenticated routes and clear all cached
   706→ content on logout.

   719→ 6.1 Container Hardening
   720→ The docker-compose.yml defines three services: app (Next.js), hocuspocus (WebSocket server), and caddy
   721→ (reverse proxy). None of these containers define memory limits, CPU limits, PIDs limits, or deploy.resources
   722→ constraints. In a production environment, a resource exhaustion attack targeting any single service could
   723→ consume all available host resources, affecting other containers and potentially the host system itself. The
   724→ Hocuspocus port (3001) is directly exposed to the host network via port mapping, bypassing Caddy's TLS
   725→ termination and security headers.
   726→
   727→ Recommended hardening measures include adding resource limits to all containers (e.g., 2 CPU cores and
   728→ 2GB memory for the app container, 1 CPU core and 1GB for Hocuspocus), removing the direct port mapping
   729→ for Hocuspocus in favor of internal Docker network communication only accessible via the Caddy reverse
   730→ proxy, and ensuring all containers run with non-root user privileges. The Dockerfile should be audited to
   731→ confirm USER directives are present and no privileged operations are performed during the build process.
   732→
   733→
   734→ 6.2 Reverse Proxy and Security Headers
   735→ The Caddy reverse proxy handles TLS termination and forwards requests to the Next.js application. The
   736→ Next.js middleware generates comprehensive security headers including HSTS with 2-year max-age,
   737→ includeSubDomains, and preload directives. X-Frame-Options is set to DENY, X-Content-Type-Options to
   738→ nosniff, Referrer-Policy to strict-origin-when-cross-origin, and Cross-Origin-Opener-Policy to same-origin.
   739→ API routes receive a stricter CSP: default-src none with frame-ancestors none. However, the page-level CSP
   740→ contains unsafe-inline and unsafe-eval in the script-src directive, which undermines the otherwise
   741→ well-configured security header posture.
   742→
   743→ The in-memory rate limiting implemented in the middleware is effective for single-server deployments but
   744→ becomes ineffective in serverless environments (Vercel Edge Functions) or horizontal scaling scenarios where
   745→ each instance maintains independent rate limit state. The codebase includes a TODO comment noting that
   746→ production should use Redis-backed rate limiting (Upstash), but this has not been implemented. The IP
   747→ extraction logic correctly prioritizes X-Real-IP over X-Forwarded-For and validates against a trusted proxy
   748→ range,      but     falls    back   to   trusting   X-Forwarded-For      without    proxy     validation    when
   749→ TRUSTED_PROXY_RANGE is not configured.
   750→
   751→
   752→ 6.3 Secret Management
   753→ Environment secrets are accessed via process.env variables throughout the codebase, which is the correct
   754→ approach for Next.js applications. The .env file is properly listed in .gitignore, and the committed .env contains
   755→ only a local SQLite database path. The Stripe integration correctly validates that secret keys are not set to
   756→ TODO placeholder values before use. However, the LiveKit integration contains multiple code paths that
   757→ silently degrade or skip authentication when secrets are not properly configured, which is a dangerous pattern
   758→ that can mask configuration errors as security vulnerabilities in production deployments.
