1. Executive Summary
This report presents the findings of a comprehensive white-box security audit conducted
on the Superboard platform, a K-12 AI-powered tutoring whiteboard application. The audit
followed a zero-gap master plan specifically designed for real-time collaborative
whiteboards and virtual classrooms, covering all five critical phases: real-time engine
and state synchronization, role-based authorization and session privacy, frontend canvas
performance and memory management, WebRTC media and infrastructure security, and
compliance with data privacy regulations.
The audit examined the complete source codebase comprising over 60 source files across
the Next.js 16 frontend, API routes, middleware, Hocuspocus collaboration server,
WebSocket examples, infrastructure configuration (Caddyfile), database schema (Prisma),
and all supporting libraries. Static code analysis, dependency scanning, and manual code
review were performed against the CVSS 3.1 scoring framework.

The most critical findings include a Server-Side Request Forgery (SSRF) vulnerability in
the Caddyfile that allows proxying traffic to any localhost port, hardcoded production
database credentials in version-controlled shell scripts, and the complete absence of
real-time CRDT synchronization implementation despite marketing claims. Additionally, the
client-side Zustand store exposes tier and authorization state to trivial console-based
tampering, the Hocuspocus collaboration server has incomplete authentication with
commented-out room access checks, and multiple API routes lack proper authentication or
authorization verification.
From a positive perspective, several security controls are properly implemented: the
Content Security Policy uses cryptographically secure nonces, KaTeX rendering correctly
disables LaTeX trust mode, Stripe webhook signature verification is in place, API keys
are properly guarded with TODO-key detection patterns, and the database schema includes
well-placed indexes and cascade delete constraints. The next.config.ts correctly sets
security headers and isolates server-only packages from client bundles.

2.2 Analysis Techniques
The audit utilized multiple complementary analysis techniques to ensure zero-gap
coverage. First, pattern-based searches were conducted across the entire codebase for
dangerous code patterns including eval(), dangerouslySetInnerHTML, innerHTML, __proto__,
Function() constructor calls, and prototype pollution vectors. Second, secret exposure
scanning searched for hardcoded credentials, API keys, and sensitive tokens in source
code and Git history. Third, all API routes were analyzed for authentication
requirements, input validation completeness, authorization checks, and rate limiting
coverage. Fourth, the dependency tree was scanned for known vulnerabilities using npm
audit. Finally, infrastructure configuration was reviewed for SSRF, TLS, CORS, and
reverse proxy misconfigurations.
2.3 Scoring Framework
All vulnerabilities are scored using the Common Vulnerability Scoring System (CVSS)
version 3.1. The severity ratings follow the standard CVSS qualitative ratings: Critical
(9.0-10.0), High (7.0-8.9), Medium (4.0-6.9), Low (0.1-3.9), and Informational (0.0).
Each finding includes explicit steps to reproduce, impact assessment, affected component
identification, and prioritized remediation recommendations.

3.2 Request Flow Architecture
Client requests flow through Caddy (port 81) which acts as a reverse proxy to the Next.js
standalone server (port 3000). The Next.js middleware intercepts every request to inject
CSP nonces, enforce rate limits via an in-memory Map store, and handle custom domain
routing for agency white-labeling. API routes use a requireAuth helper that validates
Supabase JWTs via the service role key, granting full database access bypassing Row Level
Security. The frontend uses a Zustand store for client-side state management, with
real-time collaboration intended to be handled by a separate Hocuspocus server process.
LiveKit handles WebRTC video through a token-based authentication flow. Stripe webhooks
process payment events via signature verification.

3.3 Critical Architecture Observations
Several architectural decisions have significant security implications that are worth
noting before diving into the detailed findings. First, the use of the Supabase service
role key in the server client completely bypasses Row Level Security, meaning all
authorization must be implemented at the application level in each API route. This is a
high-risk pattern because any missed authorization check in a single API route directly
exposes data. Second, the in-memory rate limiter in middleware is per-instance only and
ineffective in multi-instance deployments or serverless environments, meaning rate
limiting protection can be trivially bypassed. Third, the real-time collaboration system
(Hocuspocus/Yjs) has incomplete authentication with commented-out room access
verification, creating a potential unauthorized access vector. Fourth, the Zustand store
holds tier and authorization state client-side, making all premium feature gates
trivially bypassable through browser console manipulation.

4. Phase 1: Real-Time Engine & State Sync
Interactive whiteboards depend on synchronizing vector paths across multiple concurrent
users with minimal latency. This phase examines the WebSocket handshake authentication,
mid-session token handling, payload validation, and the CRDT synchronization engine. The
Superboard platform uses Hocuspocus as the collaboration server backed by Yjs for
conflict-free replicated data types, with Tldraw v5 as the canvas rendering engine.
4.1 WebSocket & Signaling Security
4.1.1 Hocuspocus Authentication Incomplete
The Hocuspocus collaboration server (mini-services/hocuspocus-server/index.ts, lines
64-73) implements an onAuthenticate hook that requires a userId parameter in the
connection context. However, the authentication logic never actually verifies the
provided token against the database or Supabase Auth. Any WebSocket connection that
provides a userId string in the context will be accepted as authenticated, regardless of
whether the user exists or the token is valid. Additionally, the room access verification
code is entirely commented out, meaning the server does not check whether the connecting
user is authorized to access the specific room they are requesting.
// mini-services/hocuspocus-server/index.ts lines 64-73 onAuthenticate: async (context) => { const userId
= context.context.userId; if (!userId) throw new Error("Authentication failed"); // TODO: Verify token
against database // Room access check is COMMENTED OUT: // const room = await db.room.findFirst(...) //
if (!room) throw new Error("Room not found"); }
This finding is particularly concerning in a K-12 educational context where unauthorized
access to a tutoring session could expose minor student data to unauthorized parties. An
attacker who discovers the Hocuspocus server endpoint could connect to any active room,
observe all whiteboard content, and inject their own strokes or messages by simply
providing any arbitrary userId value in the connection context.
4.1.2 Real-Time Collaboration Not Implemented
Despite marketing claims of "real-time collaboration" across the landing page and SEO
metadata, the actual CRDT synchronization code is entirely absent from the codebase. The
Whiteboard.tsx component contains only commented-out TODO code for Yjs initialization
(lines 63-94), and no yjs-provider.tsx file exists anywhere in the project. The entire
Hocuspocus connection flow, WebSocket room joining, presence synchronization, and cursor
sharing features are planned but unimplemented. The whiteboard currently renders a static
placeholder that never resolves to an actual interactive canvas.
While this is not a direct security vulnerability in the current state, it represents a
significant risk when the feature is eventually implemented without proper security
review. The CSP directive already allows connections to wss://*.hocuspocus.com and
https://*.hocuspocus.com (middleware.ts line 116), creating an unnecessarily broad attack
surface for a feature that does not yet exist. The Hocuspocus server exists as a separate

4.2 Canvas State Synchronization
Since the real-time CRDT synchronization is not yet implemented, the following findings
are forward-looking assessments based on the codebase as it currently stands:
• Concurrency Engine (OT/CRDT): No CRDT engine is active. When implemented, Yjs will
provide conflict-free merging, but the lack of server-side validation on incoming
Yjs updates means malicious clients could inject arbitrary document states.
• Out-of-Order Packet Resolution: No network resilience testing was possible as no
sync occurs. Yjs provides built-in ordering guarantees, but the middleware CSP
allows wildcard Hocuspocus domains, which could be exploited if DNS rebinding
attacks redirect WebSocket connections.
• State Snapshot Ingestion: BoardPage.snapshot and Template.snapshot fields in the
Prisma schema are unbounded String fields with no size limits. A malicious or buggy
client could store enormous serialized Yjs documents, causing database bloat and
potential denial of service.
• Network Reconnection: No reconnection logic exists. The Tldraw editor reference
(editorRef) is null and never populated. When CRDT is implemented, proper
reconnection with fresh state snapshots must be enforced to prevent local state
corruption.

5. Phase 2: Role-Based Authorization &
Privacy
Virtual classrooms require strict role separation between tutors and students. A student
must never be able to impersonate a tutor, access hidden answer keys, or tamper with
global room state. This phase examines the RBAC implementation, privilege escalation
vectors, room isolation boundaries, and multi-tenancy enforcement.
5.1 RBAC & Privilege Escalation
5.1.1 Client-Side Tier/Role Bypass via Zustand Store
The entire authorization and tier system relies on client-side Zustand store state
(src/store/app-store.ts, 171 lines). The store maintains isTutor, tier, aiCreditsUsed,
aiCreditsLimit, and participants array entirely in memory with no server synchronization.
Any user can open the browser developer console and execute store mutations to bypass all
authorization checks. The following console commands demonstrate complete privilege
escalation:
// Bypass tutor check useAppStore.setState({ room: { ...useAppStore.getState().room, tutorId: user.id } });
// Bypass tier/paywall useAppStore.setState({ tier: "AGENCY" }); // Bypass AI credit limits
useAppStore.setState({ aiCreditsUsed: 0, aiCreditsLimit: 999999 }); // Unlock AI panel
useAppStore.getState().toggleAIPanel();
While some premium API endpoints re-verify tier server-side (e.g., /api/ai/action checks
tier and deducts credits), the client-side checks in toolkits, video recording, and
premium features serve as the primary gate for the user experience. A student who
bypasses the client-side tutor check can view the answer key modal shell, access premium
toolkit panels, and see the AI control panel before the server rejects the actual API
call. This creates a confusing user experience and leaks information about premium
features to free-tier users.
5.1.2 Answer Key Client-Side Guard Bypassable
The AnswerKeyModal component (src/components/ai/AnswerKeyModal.tsx, line 117) implements
an early exit if isTutor is false, returning null to hide the modal. However, the isTutor
value is read from the Zustand store, which is trivially spoofable from the browser
console. While a server-side verification POST to /api/ai/answer-key does exist, the
client-side guard renders the Dialog shell even before server verification completes if
isTutor is spoofed. This leaks the existence and structure of the answer key modal to
students. The server should return the actual answer data itself rather than a boolean
verification, ensuring the modal only displays content that the server has explicitly
authorized.

5.2 Room Isolation & Multi-Tenancy
5.2.1 Unauthenticated Room Data Exposure
The /api/room GET endpoint (src/app/api/room/route.ts) allows fetching complete room data
including all page snapshots, tutor information, and branding data without any
authentication. The endpoint uses verifyAuth (optional) instead of requireAuth, and the
room page (src/app/room/[roomId]/page.tsx, line 27) explicitly fetches room data without
auth with the comment "no auth needed - students access this too." While room IDs are
UUID v4 (hard to guess), any leaked room URL, shared link, or URL referrer header exposes
the full room content to anonymous users.
This is particularly concerning in a K-12 context where tutoring sessions may contain
sensitive student work, proprietary teaching materials, and personally identifiable
information. An unauthenticated user accessing a room URL can view all whiteboard
content, page snapshots, tutor identity, and branding data without leaving any audit
trail.
5.2.2 Unauthenticated Participant Injection
The /api/room/participants POST endpoint (src/app/api/room/participants/route.ts) allows
anyone to inject participants into any active room without authentication. The endpoint
accepts a roomId and studentIdentity, and upserts a participant record with no
verification that the caller is authorized to join that room or that the room is still
active. This enables several attack vectors: fake participant injection to disrupt room
participant counts, enumeration of active rooms by probing UUIDs (though impractical at
scale), and potential data injection if participant records contain additional fields.

6. Phase 3: Frontend Canvas Performance &
Memory
A 90-minute tutoring session can generate tens of thousands of vector paths. Poor memory
management will crash client browser tabs, especially on the lower-tier devices common in
K-12 educational settings. This phase examines vector path optimization, canvas rendering
efficiency, event throttling, and memory leak potential.
6.1 Vector Path & Rendering
• Path Simplification: The ImageCompressor component exists but no path simplification
(e.g., Douglas-Peucker) is applied to raw pointer/touch coordinates before
transmission. The Tldraw v5 engine may handle this internally, but no explicit path
smoothing was found in the codebase.
• Canvas Object Garbage Collection: No explicit GC management for deleted shapes.
Tldraw v5 handles this internally, but without a functioning CRDT sync, there is no
server-side persistence to test memory behavior over extended sessions.
• Offscreen Canvas: Tldraw v5 uses an optimized rendering pipeline with offscreen
canvas support. However, the whiteboard is not mounted in the current codebase
(Whiteboard.tsx shows a static placeholder), so no rendering performance could be
assessed.
6.2 Event Throttling & Device Compatibility
High-frequency pointer events (pointermove, touchmove) are handled by the Tldraw v5
engine which implements built-in throttling and batching. No custom throttling was found
in the Toolbar or Whiteboard components. The application uses responsive design via
Tailwind CSS but no device-specific performance profiling was possible since the
whiteboard is not functional in the current build. The monolithic page.tsx (1,523 lines)
is a significant concern for initial bundle size and parse time on lower-end devices, as
it combines the landing page, dashboard, billing, saved boards, templates, and agency
admin panels in a single component.
The God file anti-pattern in page.tsx combines five distinct UI sections that should be
separate route-level components. This monolithic structure increases initial JavaScript
parse/compile time, reduces code splitting effectiveness, and makes it difficult to
implement per-section lazy loading or error boundaries. The component uses multiple bare
fetch calls with manually attached Bearer tokens instead of the authFetch abstraction,
creating inconsistencies in token handling and error management.

7. Phase 4: WebRTC Media & Infrastructure
If the platform includes audio, video, or screen sharing alongside the whiteboard, media
streams must be audited for security and scalability. This phase also covers the broader
infrastructure security including static code analysis, secret leakage detection, and
deployment hardening.
7.1 WebRTC / SFU Security
7.1.1 LiveKit Placeholder Token Generation
The LiveKit token endpoint (src/app/api/livekit/token/route.ts) currently generates
placeholder JWT tokens when the LIVEKIT_API_KEY environment variable starts with "TODO_".
The placeholder token is a hardcoded base64 JWT with a "mock_signature" that would fail
to connect to a real LiveKit SFU server. While this is appropriate for development, if
the environment variable is misconfigured in production (e.g., empty string), the
endpoint silently generates mock tokens without throwing an error, creating a scenario
where video features appear to work but never actually connect. Additionally, LIVEKIT_URL
is exported from livekit.ts (line 66), which could leak infrastructure details if this
file is accidentally imported client-side.

7.3 Secrets & Credential Exposure
7.3.1 CRITICAL - Production Database Credentials in Source Code
Production database connection strings containing the actual password are hardcoded in
version-controlled shell scripts. The password "thephisics1" provides full read/write
access to the Supabase PostgreSQL database. These credentials appear in the following
files:
# scripts/start-dev-server.sh (lines 26, 54) DATABASE_URL="postgresql://postgres.ruygzmkqtdogtencjdzg:
thephisics1@aws-0-ap-southeast-1.pooler.supabase.com:6543/postgres" # scripts/run-dev.sh (line 3)
export DATABASE_URL="postgresql://postgres.ruygzmkqtdogtencjdzg:
thephisics1@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres"
Anyone with repository access has full database read/write access. The password is a real
credential, not a placeholder. The different ports (6543 for PgBouncer pooler, 5432 for
direct connection) suggest these scripts were used in both development and production
contexts. These credentials must be immediately rotated and replaced with environment
variable references.
7.3.2 Hardcoded Test Account Passwords
The seed script (scripts/seed-users.ts, lines 27-52) contains four test accounts with
hardcoded passwords that are real Supabase Auth credentials. If the codebase is ever made
public, these accounts are immediately compromised. The accounts include student,
free-tutor, pro-tutor, and agency roles with passwords following a predictable pattern
(RoleName1234!). These should be moved to environment variables or a .env.secrets file
excluded from version control.
7.3.3 Caddyfile SSRF Vulnerability
The Caddyfile (lines 3-13) implements a query parameter-based port transformation that
allows proxying traffic to any localhost port. An attacker can send a request to
http://target:81/?XTransformPort=6379 to proxy traffic to Redis (6379), PostgreSQL
(5432), or any internal service. This is a textbook Server-Side Request Forgery (SSRF)
vulnerability with critical severity. The Caddy configuration also lacks TLS termination
(HTTP only on port 81), trusted proxy configuration (enabling IP spoofing to bypass rate
limits), request size limits, and access logging.

8. Phase 5: Compliance, Recording &
Privacy
Virtual classrooms process sensitive student data and minor interaction records. This
phase examines session recording security, data retention policies, and compliance with
relevant regulations. While the platform is still in development and may not yet be
subject to mandatory compliance, establishing proper practices early is essential.
8.1 Session Recording
The RecordButton component (src/components/video/RecordButton.tsx) has recording
start/stop API calls entirely commented out as TODO. Recording state is toggled locally
but never persisted to the server. When recording is implemented, the following controls
must be in place: recorded whiteboard sessions must be encrypted in transit (TLS 1.3) and
at rest (AES-256), links to saved recordings must use signed URLs with short expiration
durations, and recordings must be accessible only to authorized participants (tutor and
agency administrators).
8.2 Data Retention & Privacy
No explicit data retention policies are implemented in the codebase. Student identities
are stored in the RoomParticipant table with no TTL or automatic purge mechanism. The
fingerprint-based usage tracking (fingerprint.ts) generates browser fingerprints that
constitute personally identifiable information under GDPR. The agency branding logo URLs
accept any HTTPS domain without validation, creating a potential tracking vector. For
COPPA/FERPA compliance, the platform will need to implement: explicit parental consent
mechanisms for students under 13, data minimization practices (only collect necessary
data), the right to delete student data upon request, and audit logging of all access to
student records.
The current Supabase configuration uses the service role key which bypasses all Row Level
Security. This means there are no database-level access controls protecting student data.
All authorization is application-level only, and any bug in an API route authorization
check directly exposes data. For COPPA compliance, this is particularly concerning as
student identities, canvas content, and interaction history are all accessible through
API routes that may have incomplete authorization checks.

8.3 robots.txt Configuration
The current robots.txt allows all user agents with full access to the entire site.
Internal pages such as /api/ routes, /room/ pages, /invite/ pages, and /dashboard routes
should be disallowed to prevent search engine indexing of sensitive user content. The
recommended configuration adds Disallow directives for /api/, /room/, /invite/, and other
internal paths while maintaining Allow for the landing page and marketing content.

10. Architecture & Bottleneck Report
This section provides a deep-dive analysis of architectural bottlenecks, latency
concerns, memory management issues, and scalability limitations identified during the
audit. Each bottleneck is assessed for its impact on system reliability, user experience,
and the ability to handle production load.
10.1 Authentication Architecture Bottleneck
The Supabase service role key is used for all server-side database operations, completely
bypassing Row Level Security. This architectural decision creates a single point of
failure for data protection. Any API route that misses an authorization check exposes
data directly, with no database-level safety net. The current architecture relies on each
individual API route correctly implementing authorization checks, which is error-prone
and does not scale as the codebase grows. A recommended approach is to implement a
middleware-level authorization layer that extracts the user context from the JWT and
injects it into the request object, with route-level declarations of required permissions.
10.2 Rate Limiting Ineffectiveness
The in-memory rate limiter (middleware.ts lines 23-60) uses a Map data structure to track
request counts per IP and endpoint category. In production deployments with multiple
Next.js instances (common with containerized or serverless hosting), each instance
maintains its own independent Map, meaning an attacker distributing requests across
instances can bypass all rate limits. The setInterval cleanup (lines 53-60) for stale
entries may not function reliably in Edge Runtime environments where idle instances are
terminated. Additionally, the IP extraction trusts the X-Forwarded-For header (line 81)
which is trivially spoofable without proper trusted proxy configuration. A Redis-backed
rate limiter (e.g., Upstash Redis) is recommended for multi-instance deployments.
10.3 Database Schema Bottlenecks
Several database schema design choices create potential bottlenecks. The
BoardPage.snapshot and Template.snapshot fields are unbounded String fields that store
serialized Yjs documents. A single document could be megabytes in size, and Prisma loads
these into memory on every query that touches the parent model. The User.tier field is a
free-form String with no database-level enum constraint, meaning any value can be
inserted. The AgencyInvite.status field has the same issue. Database-level constraints
would provide defense-in-depth against application-level validation bugs.

10.4 Frontend Bundle Size Concern
The monolithic page.tsx at 1,523 lines combines the landing page, authenticated
dashboard, billing panel, saved boards, templates, and agency admin into a single
component. This anti-pattern prevents effective code splitting and increases initial
JavaScript parse time. The Zustand store (171 lines) is imported by multiple components
but has no persistence middleware, meaning all state is lost on page refresh. The Tldraw
v5 integration with optimizePackageImports in next.config.ts helps with tree-shaking, but
the overall bundle architecture needs refactoring to support lazy loading of heavy
features like the whiteboard editor, video conferencing, and AI panels.

V-01: Remove Caddyfile SSRF Handler
Immediately remove the @transform_port_query block from the Caddyfile. This handler

V-02: Rotate and Remove Hardcoded DB Credentials

11.2 HIGH Remediations

should: (1) Extract the JWT from the connection context or headers, (2) Verify the JWT
signature against the Supabase JWT secret, (3) Check that the user exists in the
database, (4) Verify the user has access to the requested room (tutor, participant, or
valid invite code). Uncomment and complete the room access verification code that is
currently commented out.

12. Verification & Re-Testing Plan
After implementing the remediation patches, a structured verification and re-testing pass
must be conducted to certify that all reported issues have been properly resolved without
introducing regressions. This section defines the verification methodology and acceptance
criteria for each severity level.
12.1 Verification Methodology
• CRITICAL Findings (V-01 to V-03): Manual verification by a second reviewer. Must
demonstrate that the vulnerability no longer exists through explicit
proof-of-concept testing. Credential rotation must be confirmed with database logs
showing the old password is rejected.
• HIGH Findings (V-04 to V-11): Automated test suite + manual verification. Each
finding must have at least one automated test case that fails before the fix and
passes after. Manual penetration testing to confirm the fix is effective.
• MEDIUM Findings (V-12 to V-25): Automated test coverage for most findings. Code
review to confirm the fix follows the recommended pattern. Integration testing for
endpoint-level fixes.
• LOW/INFO Findings (V-26 to I-06): Code review confirmation. ESLint rule additions
verified by running the linter. No regression testing required for informational
items.
12.2 Acceptance Criteria
The following acceptance criteria must be met before sign-off: all CRITICAL and HIGH
findings must be verified as fixed with documented evidence; the build must succeed
without errors (next build); all existing functionality must work correctly (manual smoke
test of core user flows); no new vulnerabilities must be introduced by the remediation
changes; and automated test coverage must exist for all CRITICAL and HIGH findings.

Stripe checkout and webhook processing, LiveKit video connection, and agency admin

tested in both FREE and PRO/AGENCY tiers to verify that authorization boundaries remain
intact.
