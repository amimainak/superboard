Executive Summary
This report presents the findings of a comprehensive white-box audit of the Superboard platform, a
K-12 AI-powered tutoring whiteboard application. The audit was conducted with full access to the
source code, database schema, server configuration, and API routes. Five distinct audit categories
were examined: functional testing, security penetration testing, performance analysis, UX/UI
accessibility compliance, and code quality assessment. The findings reveal that while the
authentication framework and database layer are fundamentally sound, significant portions of the
application remain in a scaffolded or non-functional state, with several critical security vulnerabilities
requiring immediate remediation before any public launch.

The overall assessment indicates that Superboard is in a pre-alpha architectural stage. The core
scaffolding (Supabase authentication, Prisma ORM, Stripe webhooks, agency management)
demonstrates competent design patterns. However, the primary user-facing features (whiteboard
drawing, AI integration, video conferencing, recording, PDF export, and GeoGebra integration) are
all placeholder implementations that return mock data or log to console. From a security
perspective, the absence of rate limiting across all endpoints and the completely unauthenticated

accessibility violations, including missing landmark elements, absent keyboard navigation for the
video panel, and insufficient color contrast ratios. Addressing these findings in priority order is
essential before the platform can be considered ready for beta testing or public access.

Audit Methodology
This audit employed a white-box methodology, meaning the auditor had complete access to the
application source code, database schema, server configuration files, environment variable handling
patterns, and dependency manifests. This approach provides the deepest possible analysis
compared to black-box testing, as it reveals vulnerabilities that may not be discoverable from the
user interface alone, such as secret leakage patterns, improper authorization checks in API routes,
and database query inefficiencies.
1.1 Scope
•
Source Code: All 66+ files under src/, including pages, components, hooks, libraries,
stores, types, and middleware. Also includes prisma/schema.prisma, next.config.ts,
tailwind.config.ts, Caddyfile, and package.json.
•
API Routes: All 17 API endpoints under src/app/api/ were individually analyzed for
authentication, authorization, input validation, error handling, and data exposure.
•
Components: All 23 custom application components were audited for props validation,
accessibility, memory leaks, XSS risks, state management, and responsive design.
•
Infrastructure: Build configuration, deployment scripts, Hocuspocus real-time server, and
reverse proxy configuration were reviewed.
•
Dependencies: npm audit was run to identify known vulnerabilities. Bundle analysis was
performed via Next.js build output.
1.2 Tools & Techniques
•
TypeScript Compiler: npx tsc --noEmit was run to inventory all 72 TypeScript errors hidden
by ignoreBuildErrors: true.
•
npm audit: Automated vulnerability scanning identified 25 vulnerabilities (1 critical, 15 high,
7 moderate, 2 low).
•
Next.js Build Output: Bundle analysis revealed 1.7 MB of client JavaScript across 33
chunks.
•
WCAG 2.1 Analysis: Manual code review against all three WCAG levels (A, AA, AAA) for
perceivable, operable, understandable, and robust criteria.
•
OWASP Patterns: API routes were tested against OWASP Top 10 patterns including
injection, broken authentication, sensitive data exposure, and missing rate limiting.

1.3 Button & Workflow Testing
Every interactive element on the landing page, dashboard, room view, and settings panel was
traced through the code to verify that click handlers are wired to real logic. The analysis identified
several buttons that appear functional but perform no meaningful action when clicked, as well as
critical navigation flows that are broken or lead to dead ends.
[HIGH] AI Credits Deducted for Placeholder Responses
The /api/ai/action route deducts AI credits from the user account on every successful request, but
always returns a hardcoded placeholder JSON response regardless of whether the Anthropic API
key is configured. This means users are charged credits for responses that contain no actual AI
content. The callTextAI and callVisionAI functions in lib/ai.ts are dead code that is never called by
the API route.
File: src/app/api/ai/action/route.ts:85-96
[HIGH] Stripe Checkout Route Does Not Exist
The PaywallModal component directs PRO upgrade clicks to /api/stripe/checkout?plan=pro, but this
API route does not exist in the codebase. Clicking the upgrade button results in a 404 error. Only
the webhook handler at /api/stripe/webhook is implemented, meaning there is no way for users to
actually initiate a subscription payment.
File: src/components/premium/PaywallModal.tsx:89
[MEDIUM] Settings Gear Icon Has No Click Handler
The settings gear icon in the dashboard header renders a button element but the onClick handler
calls setShowSettings, which is not defined as state in the component. This results in a silent
runtime error when clicked, and the settings panel never opens.

2. Section 2: Security Audit & Penetration
Testing
The security audit examined the application for vulnerabilities across the OWASP Top 10
categories, focusing on authentication bypasses, authorization flaws, injection risks, sensitive data
exposure, and infrastructure-level weaknesses. The findings are presented in severity order, from
critical issues that could lead to immediate exploitation to lower-severity concerns that represent
defense-in-depth improvements. All API routes were analyzed for proper authentication
requirements, input validation practices, and safe data handling.
2.1 Critical Vulnerabilities
[CRITICAL] No Authentication on LiveKit Token Endpoint
The POST /api/livekit/token endpoint has absolutely no authentication check. Any anonymous user
who knows or guesses a room ID can obtain a LiveKit token and join any active video session. The
endpoint accepts arbitrary roomId, userId, and userName parameters without verification. An
attacker could enumerate room IDs, impersonate any user, and potentially eavesdrop on tutoring
sessions. The token generated is a mock JWT with a fake signature, but if this endpoint is
connected to a real LiveKit server without adding authentication, the consequences would be
severe. Even with the mock token, the endpoint leaks room existence and user identity patterns.
File: src/app/api/livekit/token/route.ts
[CRITICAL] No Rate Limiting on Any Endpoint
Not a single API route in the entire application implements rate limiting. No rate-limit library is
installed, no middleware-level throttle exists, and no custom rate-checking logic is present anywhere
in the codebase. This means all endpoints are vulnerable to brute-force attacks, credential stuffing,
and 
denial-of-service. 
Specific 
attack 
vectors 
include: 
enumerating 
valid 
emails 
via
/api/auth/register, brute-forcing 8-character invite codes on /api/agency/invite/[code], exhausting AI
credits on behalf of users by replaying requests, and flooding the database with rapid polling on
usage and room endpoints.
File: All API routes under src/app/api/
[CRITICAL] Secret Keys Exported from Client-Accessible Modules
Several library files export secret API keys as named exports. Specifically, LIVEKIT_API_SECRET
is exported from lib/livekit.ts, STRIPE_SECRET_KEY and STRIPE_WEBHOOK_SECRET from
lib/stripe.ts, and MATHPIX_APP_KEY from lib/mathpix.ts. While Next.js tree-shaking currently
prevents these from reaching the client bundle, any future refactoring that imports these modules
from a client component would leak secrets to the browser. This is a ticking time bomb that violates
the principle of defense in depth. Secrets should be accessed via environment variables only within
API route handlers.

2.2 Authentication & Authorization
[HIGH] Room Participants Endpoint Has No Authentication
Both GET and POST requests to /api/room/participants work without any authentication. Anyone
can list all participants in any room (information disclosure) and anyone can join any active room as
any identity. The POST handler accepts arbitrary studentIdentity and studentName values with no
format validation or length limit, allowing an attacker to spam fake participants or store arbitrary data
in the database. For agency billing which counts unique participants, this could be exploited to
inflate billing charges.
File: src/app/api/room/participants/route.ts
[HIGH] Answer Key Security is Client-Side Only
The AnswerKeyModal component gates visibility using if (!isTutor) return null, which is a client-side
check. A student could open browser DevTools, modify the Zustand store to set isTutor: true, and
view all answer keys for any quiz or worksheet. The modal also displays a misleading "Encrypted"
footer claim, when there is no actual encryption implemented. Answer keys should be fetched from
a server-side endpoint that verifies tutor status before returning data.
File: src/components/ai/AnswerKeyModal.tsx
[HIGH] Hocuspocus Server Accepts All Connections
The Hocuspocus real-time collaboration server at mini-services/hocuspocus-server/index.ts has an
onAuthenticate hook that accepts any connection without verifying room access. The comment
indicates this is intentional for development, but if deployed to production, any user could connect to
any room and modify the whiteboard document. All persistence hooks are also commented out,
meaning documents exist only in memory and are lost on server restart.
File: mini-services/hocuspocus-server/index.ts
[MEDIUM] Invite Information Leakage
The GET /api/agency/invite/[code] endpoint leaks internal state to unauthenticated users. The error
response includes detail: Status: ACCEPTED or Status: CANCELLED, which reveals whether an
invite was sent and its outcome. Additionally, accessing an expired invite triggers an automatic
status update to EXPIRED, meaning a scanner probing random codes can trigger mass status
changes. The GET response also exposes the agency name, branding information, and the invited
email address to anyone with the code.
File: src/app/api/agency/invite/[code]/route.ts
[MEDIUM] Room Details Leaked to Unauthenticated Users
The GET /api/room endpoint returns room details including the tutor name, tier, subject, and full
board page snapshots to anyone who provides a valid room ID. No authentication is required to

2.3 Data Exposure & Input Risks
[MEDIUM] No Input Validation Library Used (Zod Installed But Unused)
Zod is listed as a dependency (version ^4.0.2) but is never imported in any API route. All validation
consists of manual if (!field) checks, which means there are no type-safe parsers, no maximum
length checks on strings, no enum validation beyond manual comparisons, and no schema reuse
between client and server. The prompt parameter to the AI action endpoint has no length limit, and
imageBase64 has no size limit, creating potential memory exhaustion vectors.
File: All API routes
[MEDIUM] KaTeX trust: true Enables HTML Injection
The KaTeX rendering configuration in lib/katex.ts sets trust: true, which allows LaTeX commands
like \html{...} to render raw HTML. If user-controlled LaTeX content (e.g., from the AI response or
student input) is rendered with this configuration, it creates a cross-site scripting (XSS) vector.
Additionally, strict: false suppresses KaTeX error reporting, meaning malformed input fails silently
rather than being rejected.
File: src/lib/katex.ts:23
[MEDIUM] Agency Logo URL Not Validated (Potential XSS)
The BrandedHeader and WaitingRoom components render agency-controlled logoUrl values
directly in img src attributes. If an agency tutor sets their logoUrl to a javascript: URI or a data URI
containing malicious content, it could execute in the user browser context. The URL should be
validated to ensure it points to an allowed domain and uses an acceptable protocol (https).
File: src/components/branding/BrandedHeader.tsx:33, src/components/student/WaitingRoom.tsx:138

Several API routes fetch the same user record multiple times within a single request. These
redundant queries add unnecessary database load and increase response latency. The most
egregious cases are listed below with specific line references and recommended consolidation
strategies.
•
room/route.ts (lines 144 + 173): Room is fetched twice with findUnique. The first fetch
excludes tutor email for students; the second re-fetches including email for the tutor. This
should be a single query with conditional include based on authentication status.
•
usage/current/route.ts (lines 30, 40, 52): User record is looked up three times. Lines 30
and 52 query the same user when a user checks their own usage. These should be
consolidated into a single query with all needed includes.
•
auth/profile/route.ts (lines 27, 38, 50): Same three-lookup pattern. Agency check,
sub-tutor parent check, and target user fetch all query the User table separately.
•
agency/students/route.ts (lines 18, 31, 39, 65): Four sequential queries that could be
replaced with a single aggregate SQL query using joins and group-by.
3.5 Caching & Optimization Gaps
The application has zero caching infrastructure. No Cache-Control headers are set on any API
response. No route segment config (revalidate, dynamic, fetchCache) is exported from any route.
No Next.js caching APIs (unstable_cache, use cache, revalidatePath, revalidateTag) are used
anywhere. The /api/usage/current endpoint, which is polled every 30 seconds by the UsageBar
component, hits the database on every single request. For a platform with concurrent users, this
would generate thousands of unnecessary database queries per minute. Similarly, room data is
re-fetched without any client-side or server-side caching, meaning navigating between dashboard
and room view always triggers fresh database reads.
•
Recommendation: Add Cache-Control: s-maxage=10, stale-while-revalidate=30 to
/api/usage/current.
•
Recommendation: Use Next.js unstable_cache for room listing queries with a 60-second
TTL.
•
Recommendation: Replace raw img tags with next/image for automatic lazy loading, format
conversion, and size optimization.
•
Recommendation: Tighten remotePatterns from hostname: "**" to specific allowed
domains.

4. Section 4: UX/UI & Accessibility Review
The accessibility audit evaluates the application against WCAG 2.1 standards across all four
principles: Perceivable, Operable, Understandable, and Robust. The code-based review identified
27 violations: 14 at Level A (must fix for basic accessibility), 11 at Level AA (should fix for standard
compliance), and 2 at Level AAA (nice to fix for enhanced usability). The most critical finding is that

4.2 Keyboard & Screen Reader Access
The most severe accessibility gap is the PiP (Picture-in-Picture) video panel, which relies entirely on
mouse events for all interactions. The drag-to-move functionality uses only onMouseDown with no
onKeyDown alternative. The resize handle is a div with only onMouseDown. The minimize/expand
toggle is an onClick on a div element with no tabIndex or role. All video control buttons (camera,
microphone, deafen, speaker output, and leave call) lack aria-label attributes, making them invisible
to screen reader users. A keyboard-only user cannot move, resize, minimize, or interact with the
video panel in any way.
The landing page lacks a skip-to-content link, which is a Level A requirement. Users who navigate
via keyboard must tab through the entire navigation bar on every page load before reaching the
main content. The landing page also lacks a main landmark element, wrapping all content in a plain
div instead of semantic HTML. Multiple interactive elements throughout the dashboard (Quick Start
items, board rows) are clickable divs with no role="button", tabIndex, or onKeyDown handler,
making them invisible to assistive technology and unreachable by keyboard.
4.3 Color Contrast & Visual Design
Several text elements fail the WCAG 2.1 Level AA contrast requirement of 4.5:1 for normal text. The
most common offender is text-gray-400 (#9ca3af on white), which achieves approximately 2.9:1
contrast ratio. This is used in multiple locations including the "and growing" text on the landing page,
the "No credit card required" subheading, and the footer copyright notice. The fix is straightforward:
change text-gray-400 to text-gray-500 (approximately 4.6:1 contrast) or text-gray-600 for even better
readability. In the PipVideoPanel, text-white/50 and text-white/60 on dark backgrounds may also fall
below the 3:1 requirement for non-text UI components.
Color-only indicators are used in several places without text alternatives. The invite status badges
(Pending amber, Expired gray, Accepted green) rely primarily on background color to communicate
status. The isSpeaking ring indicator in the video panel uses only a green border with no text or
ARIA equivalent. While these elements do contain text labels in some cases, the color coding
should not be the sole means of conveying information per WCAG 1.4.1.

5. Section 5: Code Quality & Architecture
Code quality assessment examines the long-term maintainability, scalability, and technical debt of
the codebase. A well-architected codebase should have clear separation of concerns, consistent
patterns, comprehensive error handling, and minimal duplication. This section identifies architectural
anti-patterns, dead code accumulation, naming inconsistencies, and structural issues that will
compound in cost as the application grows.
5.1 Architecture Assessment
[HIGH] God File: page.tsx at 1,518 Lines
The main page.tsx file contains both the entire landing page (unauthenticated) and the full
dashboard (authenticated) in a single component. This includes auth dialogs, room management,
billing panel, agency administration, settings, and invite management. At 1,518 lines, this file
violates the single responsibility principle and is extremely difficult to maintain, test, or review. Any
change to one feature area risks introducing regressions in others. The file contains multiple
complex useEffect hooks with intricate dependency arrays, inline event handlers that should be
extracted to custom hooks, and duplicate imports (useAppStore is imported on both line 11 and line
34).
File: src/app/page.tsx
[MEDIUM] No Error Boundaries Anywhere
Zero error boundary components exist in the codebase. A runtime crash in any child component
(Whiteboard, Toolbar, VideoPanel) will unmount the entire component tree and display a blank page
to the user. For a tutoring platform where users are in active sessions, this is unacceptable. React
error boundaries should wrap at least the Whiteboard container, the video panel, and the AI
generation components to provide graceful degradation.
File: All component files
[MEDIUM] Duplicate Component Code Across Toolkits
SectionLabel and LockOverlay components are identically copy-pasted across all four toolkit files
(MathToolkit, ScienceToolkit, LanguageToolkit, GeneralToolkit). While a shared ToolkitShared.tsx
file exists, the toolkits do not import from it. This means any change to these shared components
must be replicated four times, creating maintenance burden and inconsistency risk.
