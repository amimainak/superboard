   110→1. Executive Summary
   111→This report presents the findings of a comprehensive white-box security audit conducted on the Superboard
   112→platform, a real-time collaborative whiteboard and virtual classroom application built with Next.js 16,
   113→Hocuspocus (Yjs/CRDT), LiveKit (WebRTC), Tldraw (vector canvas), Supabase (authentication and
   114→database), and Stripe (payment processing). The audit examined all source code repositories, API routes,
   115→WebSocket servers, infrastructure configurations, and frontend components across five distinct audit phases as
   116→defined in the White-Box Audit Master Plan.
   117→The assessment identified a total of 52 security findings across all system layers: 10 Critical, 14 High, 18
   118→Medium, and 10 Low severity. The most severe vulnerabilities center on three primary attack surfaces: (1)
   119→missing or bypassable authentication on critical endpoints including WebSocket connections, room join
   120→operations, and parent portal access; (2) insufficient authorization enforcement allowing privilege escalation
   121→from student to tutor roles in both the real-time collaboration layer and the WebRTC media pipeline; and (3)
   122→weakened Content Security Policy that generates cryptographic nonces but fails to use them, leaving all inline
   123→script execution unrestricted.
   124→The platform demonstrates evidence of prior security remediation efforts, with multiple SECURITY FIX
   125→annotations referencing specific vulnerability identifiers (V-06 through V-34, I-02 through I-05).
   126→Authentication enforcement on API routes is generally strong, with most endpoints correctly invoking
   127→requireAuth() or requireAdmin() helpers. The Prisma ORM provides strong SQL injection protection, Zod
   128→schemas validate most user inputs, and security headers including HSTS, X-Frame-Options, and
   129→X-Content-Type-Options 
   130→are 
   131→properly 
   132→configured. 
   133→However, 
   134→the 
   135→real-time 
   136→collaboration 
   137→layer
   138→(Hocuspocus/Yjs) and the WebRTC signaling pipeline contain fundamental authentication gaps that
   139→undermine the otherwise solid application-level security.
   140→Immediate remediation of all 10 Critical findings is strongly recommended before any further production
   141→deployment. These vulnerabilities, if exploited, could allow unauthorized access to live tutoring sessions,
   142→exposure of student personally identifiable information (PII), forgery of video conferencing tokens, and
   143→server-side request forgery attacks against internal infrastructure. The estimated total remediation effort is
   144→approximately 3-4 developer-sprints, with Critical items addressable within the first sprint.

   501→3. Architecture and State Bottleneck Analysis
   502→3.1 Real-Time Engine Architecture
   503→The Superboard real-time collaboration engine is built on a three-layer architecture: Tldraw provides the
   504→vector canvas rendering on the frontend, Hocuspocus serves as the WebSocket server managing Yjs document
   505→synchronization, and PostgreSQL (via Prisma) persists document snapshots. The system uses a snapshot-based
   506→synchronization approach rather than fine-grained operational transformation, which introduces specific
   507→latency and consistency characteristics that were analyzed during this audit.
   508→The most significant architectural bottleneck identified is the snapshot-based sync mechanism in
   509→TldrawCanvas.tsx. Rather than using the official @tldraw/yjs binding that integrates Tldraw's store directly
   510→with Yjs shared types at the individual operation level, the current implementation serializes the entire editor
   511→state to JSON on each change with a 500ms debounce interval. This creates a last-writer-wins race condition
   512→
   513→=== PAGE 9 ===
   514→Superboard Security Audit Report
   515→CONFIDENTIAL
   516→Page 9
   517→where concurrent edits from multiple users result in data loss. When two users draw simultaneously, the last
   518→snapshot to arrive overwrites the other user's changes within the debounce window. This fundamentally
   519→undermines the collaborative editing experience and represents a data integrity risk in production tutoring
   520→sessions.
   521→The Hocuspocus server is configured with IP-based connection rate limiting (30 connections per minute) but
   522→lacks per-connection message rate limiting, payload size limits (maxDocumentSize is not set), and the room
   523→membership verification is entirely commented out. The persistence layer implements a 5MB size check on
   524→document snapshots but this only triggers during store operations, not on inbound WebSocket messages,
   525→meaning oversized payloads can accumulate in server memory before being rejected.
   526→3.2 WebSocket Authentication Gap
   527→The Hocuspocus server defines an onAuthenticate hook that validates Supabase JWT tokens and extracts the
   528→userId from the connection context. However, the client-side useYjsProvider hook creates the
   529→HocuspocusProvider with zero authentication parameters - no token, no parameters, and no WebSocket
   530→subprotocol authentication headers are passed. This means the WebSocket connection either fails silently (if
   531→onAuthenticate is strictly enforced by Hocuspocus v4) or, more critically, proceeds without any authentication
   532→if the hook is lenient. The room membership check within onAuthenticate is entirely commented out with a
   533→TODO note, meaning even if authentication were properly wired, any authenticated user could connect to any
   534→room's CRDT document.
   535→This represents a fundamental security gap in the real-time collaboration layer. An unauthenticated or
   536→cross-tenant attacker connecting to the WebSocket can read the full whiteboard state (all drawings, text
   537→annotations, page content) and inject arbitrary data into the document. For a tutoring platform handling student
   538→work and lesson content, this is a severe confidentiality and integrity violation. The remediation requires
   539→wiring the Supabase session token from the client to the Hocuspocus connection parameters and
   540→uncommenting and implementing the room membership verification logic.
   541→3.3 WebRTC Media Pipeline
   542→The LiveKit integration for video conferencing has two critical security weaknesses. First, the token
   543→generation endpoint trusts the client-supplied isTutor field without server-side verification against the
   544→database. When isTutor is undefined (the default when a student omits it), the expression canPublish: isTutor
   545→!== false evaluates to true, granting the student full media publishing permissions including camera,
   546→microphone, and screen sharing. Second, when the LiveKit SDK throws an error or the API key is not
   547→configured, the endpoint falls back to generating mock tokens with a trivially forgeable .mock_signature suffix
   548→or a mock_token_{roomId}_{userId} string pattern.
   549→The LiveKit webhook endpoint, which receives recording status updates, uses a static Bearer token comparison

   559→3.4 Frontend Canvas Performance Concerns
   560→The TldrawCanvas component implements canvas rendering using the Tldraw library which handles vector
   561→path rendering, object management, and viewport transformations. The snapshot-based sync approach means
   562→every 500ms, the entire canvas state is serialized and transmitted as a single JSON payload. For a 90-minute
   563→tutoring session generating tens of thousands of vector paths, this creates substantial memory pressure on both
   564→the client and server. The persistence layer stores these snapshots as Text fields in PostgreSQL with a 5MB
   565→constraint, but there is no client-side mechanism to prune deleted objects from memory or to implement
   566→incremental state compression.
   567→Input event throttling analysis shows that pointermove and touchmove events are processed at browser native
   568→frequency (typically 60-120Hz) before being debounced by the 500ms sync interval. While Tldraw handles its
   569→own rendering pipeline efficiently, the lack of intermediate point simplification (e.g., Douglas-Peucker
   570→algorithm) before JSON serialization means raw coordinate data is transmitted in full, increasing WebSocket
   571→bandwidth consumption. The combination of no client-side path simplification, snapshot-based sync, and lack
   572→of memory management creates a performance degradation risk for long-duration sessions on lower-end
   573→devices.

   691→5. Compliance, Recording and Data Privacy
   692→5.1 COPPA and FERPA Considerations
   693→The Superboard platform processes educational data from K-12 students, placing it squarely within the scope
   694→of the Children's Online Privacy Protection Act (COPPA) and the Family Educational Rights and Privacy Act
   695→(FERPA). Several identified vulnerabilities directly impact compliance with these regulations. The
   696→unauthenticated room join endpoint (API-C01) can expose student names, emails, and enrollment status to
   697→unauthorized parties. The parent portal (API-C02), while designed for legitimate parental access, lacks
   698→brute-force protection on its URL-path tokens, potentially allowing unauthorized access to student homework,
   699→lesson notes, schedule information, and tutor contact details.
   700→Recording URLs (RT-M03) are served without signed access controls, meaning anyone with the URL can
   701→download video recordings of tutoring sessions. These recordings contain video and voice data of minor
   702→students, which constitutes protected educational records under FERPA. The calendar ICS endpoint
   703→(API-C03) exposes student and tutor email addresses to anyone with a lesson UUID, constituting a personally
   704→identifiable information disclosure. Under COPPA, the platform must obtain verifiable parental consent
   705→before collecting personal information from children under 13, and the current authentication gaps could allow
   706→data collection without proper consent verification.
   707→5.2 Data Retention and Encryption
   708→The platform stores board page snapshots as Text fields in PostgreSQL with a 5MB constraint. Recordings are
   709→stored via LiveKit Egress, with URLs persisted in the Recording model. There is no evidence of
   710→encryption-at-rest configuration for PostgreSQL data, and recording storage encryption depends on the
   711→underlying LiveKit Egress configuration. The database schema does not include automatic data retention
   712→policies or TTL mechanisms for usage logs, recordings, or session data. For COPPA/FERPA compliance, the
   713→platform should implement automatic data retention limits with configurable expiry periods for student-related
   714→data, ensure all recordings are encrypted at rest using AES-256, and serve recording URLs via signed, expiring
   715→URLs rather than direct storage links.
   716→5.3 Service Worker Privacy Concerns
   717→The service worker (sw.js) implements a stale-while-revalidate caching strategy for all non-API GET requests.
   718→This means authenticated pages including the dashboard, room views, and admin panel are cached in the
   719→browser and can be served to subsequent users of the same device. On shared devices (common in school
   720→computer labs and library settings), this creates a user-to-user information leak where Student B may see
   721→Student A's dashboard content including name, email, tier, room list, and usage data before the revalidation
   722→request completes. The service worker should skip caching for authenticated routes and clear all cached
   723→content on logout.

   730→6.1 Container Hardening
   731→The docker-compose.yml defines three services: app (Next.js), hocuspocus (WebSocket server), and caddy
   732→(reverse proxy). None of these containers define memory limits, CPU limits, PIDs limits, or deploy.resources
   733→constraints. In a production environment, a resource exhaustion attack targeting any single service could
   734→consume all available host resources, affecting other containers and potentially the host system itself. The
   735→Hocuspocus port (3001) is directly exposed to the host network via port mapping, bypassing Caddy's TLS
   736→termination and security headers.
   737→Recommended hardening measures include adding resource limits to all containers (e.g., 2 CPU cores and
   738→2GB memory for the app container, 1 CPU core and 1GB for Hocuspocus), removing the direct port mapping
   739→for Hocuspocus in favor of internal Docker network communication only accessible via the Caddy reverse
   740→proxy, and ensuring all containers run with non-root user privileges. The Dockerfile should be audited to
   741→confirm USER directives are present and no privileged operations are performed during the build process.
   742→6.2 Reverse Proxy and Security Headers
   743→The Caddy reverse proxy handles TLS termination and forwards requests to the Next.js application. The
   744→Next.js middleware generates comprehensive security headers including HSTS with 2-year max-age,
   745→includeSubDomains, and preload directives. X-Frame-Options is set to DENY, X-Content-Type-Options to
   746→nosniff, Referrer-Policy to strict-origin-when-cross-origin, and Cross-Origin-Opener-Policy to same-origin.
   747→API routes receive a stricter CSP: default-src none with frame-ancestors none. However, the page-level CSP
   748→contains unsafe-inline and unsafe-eval in the script-src directive, which undermines the otherwise
   749→well-configured security header posture.
   750→The in-memory rate limiting implemented in the middleware is effective for single-server deployments but
   751→becomes ineffective in serverless environments (Vercel Edge Functions) or horizontal scaling scenarios where
   752→each instance maintains independent rate limit state. The codebase includes a TODO comment noting that
   753→production should use Redis-backed rate limiting (Upstash), but this has not been implemented. The IP
