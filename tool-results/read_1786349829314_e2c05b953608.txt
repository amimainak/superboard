   132→1. Executive Summary
   133→This report presents the findings of a comprehensive white-box security audit conducted on the Superboard
   134→platform, a real-time collaborative whiteboard and virtual classroom application built with Next.js 16,
   135→Hocuspocus (Yjs/CRDT), LiveKit (WebRTC), Tldraw (vector canvas), Supabase (authentication and
   136→database), and Stripe (payment processing). The audit examined all source code repositories, API routes,
   137→WebSocket servers, infrastructure configurations, and frontend components across five distinct audit phases as
   138→defined in the White-Box Audit Master Plan.
   139→The assessment identified a total of 52 security findings across all system layers: 10 Critical, 14 High, 18
   140→Medium, and 10 Low severity. The most severe vulnerabilities center on three primary attack surfaces: (1)
   141→missing or bypassable authentication on critical endpoints including WebSocket connections, room join
   142→operations, and parent portal access; (2) insufficient authorization enforcement allowing privilege escalation
   143→from student to tutor roles in both the real-time collaboration layer and the WebRTC media pipeline; and (3)
   144→weakened Content Security Policy that generates cryptographic nonces but fails to use them, leaving all inline
   145→script execution unrestricted.
   146→The platform demonstrates evidence of prior security remediation efforts, with multiple SECURITY FIX
   147→annotations referencing specific vulnerability identifiers (V-06 through V-34, I-02 through I-05).
   148→Authentication enforcement on API routes is generally strong, with most endpoints correctly invoking
   149→requireAuth() or requireAdmin() helpers. The Prisma ORM provides strong SQL injection protection, Zod
   150→schemas validate most user inputs, and security headers including HSTS, X-Frame-Options, and
   151→X-Content-Type-Options

   745→3. Architecture and State Bottleneck Analysis
   746→3.1 Real-Time Engine Architecture
   747→The Superboard real-time collaboration engine is built on a three-layer architecture: Tldraw provides the
   748→vector canvas rendering on the frontend, Hocuspocus serves as the WebSocket server managing Yjs document
   749→synchronization, and PostgreSQL (via Prisma) persists document snapshots. The system uses a snapshot-based
   750→synchronization approach rather than fine-grained operational transformation, which introduces specific
   751→latency and consistency characteristics that were analyzed during this audit.
   752→The most significant architectural bottleneck identified is the snapshot-based sync mechanism in
   753→TldrawCanvas.tsx. Rather than using the official @tldraw/yjs binding that integrates Tldraw's store directly
   754→with Yjs shared types at the individual operation level, the current implementation serializes the entire editor
   755→state to JSON on each change with a 500ms debounce interval. This creates a last-writer-wins race condition
   756→
   757→Page 8
   758→
   759→Superboard Security Audit Report
   760→
   761→CONFIDENTIAL
   762→
   763→where concurrent edits from multiple users result in data loss. When two users draw simultaneously, the last
   764→snapshot to arrive overwrites the other user's changes within the debounce window. This fundamentally
   765→undermines the collaborative editing experience and represents a data integrity risk in production tutoring
   766→sessions.
   767→The Hocuspocus server is configured with IP-based connection rate limiting (30 connections per minute) but
   768→lacks per-connection message rate limiting, payload size limits (maxDocumentSize is not set), and the room
   769→membership verification is entirely commented out. The persistence layer implements a 5MB size check on
   770→document snapshots but this only triggers during store operations, not on inbound WebSocket messages,
   771→meaning oversized payloads can accumulate in server memory before being rejected.
   772→
   773→3.2 WebSocket Authentication Gap
   774→The Hocuspocus server defines an onAuthenticate hook that validates Supabase JWT tokens and extracts the
   775→userId from the connection context. However, the client-side useYjsProvider hook creates the
   776→HocuspocusProvider with zero authentication parameters - no token, no parameters, and no WebSocket
   777→subprotocol authentication headers are passed. This means the WebSocket connection either fails silently (if
   778→onAuthenticate is strictly enforced by Hocuspocus v4) or, more critically, proceeds without any authentication
   779→if the hook is lenient. The room membership check within onAuthenticate is entirely commented out with a
   780→TODO note, meaning even if authentication were properly wired, any authenticated user could connect to any
   781→room's CRDT document.
   782→This represents a fundamental security gap in the real-time collaboration layer. An unauthenticated or
   783→cross-tenant attacker connecting to the WebSocket can read the full whiteboard state (all drawings, text
   784→annotations, page content) and inject arbitrary data into the document. For a tutoring platform handling student
   785→work and lesson content, this is a severe confidentiality and integrity violation. The remediation requires
   786→wiring the Supabase session token from the client to the Hocuspocus connection parameters and
   787→uncommenting and implementing the room membership verification logic.
   788→
   789→3.3 WebRTC Media Pipeline
   790→The LiveKit integration for video conferencing has two critical security weaknesses. First, the token
   791→generation endpoint trusts the client-supplied isTutor field without server-side verification against the
   792→database. When isTutor is undefined (the default when a student omits it), the expression canPublish: isTutor
   793→!== false evaluates to true, granting the student full media publishing permissions including camera,
   794→microphone, and screen sharing. Second, when the LiveKit SDK throws an error or the API key is not
   795→configured, the endpoint falls back to generating mock tokens with a trivially forgeable .mock_signature suffix
   796→or a mock_token_{roomId}_{userId} string pattern.
   797→The LiveKit webhook endpoint, which receives recording status updates, uses a static Bearer token comparison
   798→that is vulnerable to timing side-channel attacks. More critically, the authentication check is completely
   799→skipped when the LIVEKIT_WEBHOOK_SECRET environment variable starts with "TODO_" or is empty.
   800→In a production environment, this would allow any attacker to send fake recording events to manipulate
   801→recording statuses or trigger unauthorized recording state changes.

   809→3.4 Frontend Canvas Performance Concerns
   810→The TldrawCanvas component implements canvas rendering using the Tldraw library which handles vector
   811→path rendering, object management, and viewport transformations. The snapshot-based sync approach means
   812→every 500ms, the entire canvas state is serialized and transmitted as a single JSON payload. For a 90-minute
   813→tutoring session generating tens of thousands of vector paths, this creates substantial memory pressure on both
   814→the client and server. The persistence layer stores these snapshots as Text fields in PostgreSQL with a 5MB
   815→constraint, but there is no client-side mechanism to prune deleted objects from memory or to implement
   816→incremental state compression.
   817→Input event throttling analysis shows that pointermove and touchmove events are processed at browser native
   818→frequency (typically 60-120Hz) before being debounced by the 500ms sync interval. While Tldraw handles its
   819→own rendering pipeline efficiently, the lack of intermediate point simplification (e.g., Douglas-Peucker
   820→algorithm) before JSON serialization means raw coordinate data is transmitted in full, increasing WebSocket
   821→bandwidth consumption. The combination of no client-side path simplification, snapshot-based sync, and lack
   822→of memory management creates a performance degradation risk for long-duration sessions on lower-end
   823→devices.

   955→5. Compliance, Recording and Data Privacy
   956→5.1 COPPA and FERPA Considerations
   957→The Superboard platform processes educational data from K-12 students, placing it squarely within the scope
   958→of the Children's Online Privacy Protection Act (COPPA) and the Family Educational Rights and Privacy Act
   959→(FERPA). Several identified vulnerabilities directly impact compliance with these regulations. The
   960→unauthenticated room join endpoint (API-C01) can expose student names, emails, and enrollment status to
   961→unauthorized parties. The parent portal (API-C02), while designed for legitimate parental access, lacks
   962→brute-force protection on its URL-path tokens, potentially allowing unauthorized access to student homework,
   963→lesson notes, schedule information, and tutor contact details.
   964→Recording URLs (RT-M03) are served without signed access controls, meaning anyone with the URL can
   965→download video recordings of tutoring sessions. These recordings contain video and voice data of minor
   966→students, which constitutes protected educational records under FERPA. The calendar ICS endpoint
   967→(API-C03) exposes student and tutor email addresses to anyone with a lesson UUID, constituting a personally
   968→identifiable information disclosure. Under COPPA, the platform must obtain verifiable parental consent
   969→before collecting personal information from children under 13, and the current authentication gaps could allow
   970→data collection without proper consent verification.
   971→
   972→5.2 Data Retention and Encryption
   973→The platform stores board page snapshots as Text fields in PostgreSQL with a 5MB constraint. Recordings are
   974→stored via LiveKit Egress, with URLs persisted in the Recording model. There is no evidence of
   975→encryption-at-rest configuration for PostgreSQL data, and recording storage encryption depends on the
   976→underlying LiveKit Egress configuration. The database schema does not include automatic data retention
   977→policies or TTL mechanisms for usage logs, recordings, or session data. For COPPA/FERPA compliance, the
   978→platform should implement automatic data retention limits with configurable expiry periods for student-related
   979→data, ensure all recordings are encrypted at rest using AES-256, and serve recording URLs via signed, expiring
   980→URLs rather than direct storage links.
   981→
   982→5.3 Service Worker Privacy Concerns
   983→The service worker (sw.js) implements a stale-while-revalidate caching strategy for all non-API GET requests.
   984→This means authenticated pages including the dashboard, room views, and admin panel are cached in the
   985→browser and can be served to subsequent users of the same device. On shared devices (common in school
   986→computer labs and library settings), this creates a user-to-user information leak where Student B may see
   987→Student A's dashboard content including name, email, tier, room list, and usage data before the revalidation
   988→request completes. The service worker should skip caching for authenticated routes and clear all cached
   989→content on logout.

   998→6.1 Container Hardening
   999→The docker-compose.yml defines three services: app (Next.js), hocuspocus (WebSocket server), and caddy
  1000→(reverse proxy). None of these containers define memory limits, CPU limits, PIDs limits, or deploy.resources
  1001→constraints. In a production environment, a resource exhaustion attack targeting any single service could
  1002→consume all available host resources, affecting other containers and potentially the host system itself. The
  1003→Hocuspocus port (3001) is directly exposed to the host network via port mapping, bypassing Caddy's TLS
  1004→termination and security headers.
  1005→Recommended hardening measures include adding resource limits to all containers (e.g., 2 CPU cores and
  1006→2GB memory for the app container, 1 CPU core and 1GB for Hocuspocus), removing the direct port mapping
  1007→for Hocuspocus in favor of internal Docker network communication only accessible via the Caddy reverse
  1008→proxy, and ensuring all containers run with non-root user privileges. The Dockerfile should be audited to
  1009→confirm USER directives are present and no privileged operations are performed during the build process.
  1010→
  1011→6.2 Reverse Proxy and Security Headers
  1012→The Caddy reverse proxy handles TLS termination and forwards requests to the Next.js application. The
  1013→Next.js middleware generates comprehensive security headers including HSTS with 2-year max-age,
  1014→includeSubDomains, and preload directives. X-Frame-Options is set to DENY, X-Content-Type-Options to
  1015→nosniff, Referrer-Policy to strict-origin-when-cross-origin, and Cross-Origin-Opener-Policy to same-origin.
  1016→API routes receive a stricter CSP: default-src none with frame-ancestors none. However, the page-level CSP
  1017→contains unsafe-inline and unsafe-eval in the script-src directive, which undermines the otherwise
